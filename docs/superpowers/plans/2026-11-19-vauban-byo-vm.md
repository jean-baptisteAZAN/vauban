# Bring-your-own-VM (`target: existing`) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Let vauban deploy a project onto a server the user already runs: read-only SSH audit, install only what is missing, shared Caddy, same GitHub deploy pipeline, project-only destroy.

**Architecture:** A new `internal/remote` package runs scripts over the system `ssh` binary through the existing `engine.Runner` (so tests use the fake runner) and owns the read-only audit (embedded shell script → parsed facts → evaluated checks). A new `server` module replaces `infra` when `target: existing` (each module's `Plan` returns nil in the other mode). `deploy` renders mode-specific templates. The CLI (`plan`, `apply`, `destroy`, new `audit`) branches on `Config.Target`.

**Tech Stack:** Go 1.27, cobra/fang, huh v2, lipgloss v2, yaml.v3, system OpenSSH (`ssh`, `ssh-keygen`), embedded POSIX `sh` scripts.

**Spec:** `docs/superpowers/specs/2026-11-18-vauban-byo-vm-design.md`

## Global Constraints

- `target` values: `cloud` (default; empty means cloud) and `existing`. MVP behaviour for `cloud` must not change: every existing golden and test stays green without `-update`.
- `server:` block: `host` (required), `port` (default 22), `user` (required), `key` (path, `~` expanded, or the literal `agent`).
- `domain` is required when `target: existing`; `cloud`/`region`/`size` must be empty in that mode (Validate rejects them).
- Every SSH call: `ssh -p <port> -o BatchMode=yes -o StrictHostKeyChecking=accept-new -o UserKnownHostsFile=<root>/.vauban/known_hosts [-i <key> -o IdentitiesOnly=yes] <user>@<host> sh -s`, script on stdin. After the first successful connect the host key is pinned: later calls use `StrictHostKeyChecking=yes`.
- The audit script is read-only: no writes, no `sudo` except `sudo -n true` and `sudo -n sshd -T`; never prompts.
- Remote layout: deploy user `deploy` (docker group, no sudo); project dir `~deploy/apps/<project>/`; ownership marker `~deploy/apps/<project>/.vauban-owner` containing the GitHub repo slug `owner/name`; authorized_keys line suffixed ` # vauban:<project>`; Docker network `vauban`; app reachable as `<project>-app:<app_port>` on that network; site file `<sites dir>/<project>.caddy` with content `<domain> {\n\treverse_proxy <project>-app:<app_port>\n}\n`.
- vauban-managed Caddy: `/opt/vauban/caddy/{compose.yaml,Caddyfile,sites/}`, container `vauban-caddy`, image `caddy:2`, `restart: unless-stopped`, Caddyfile content exactly `import /etc/caddy/sites/*.caddy\n`, `sites/` owned by `deploy`.
- Existing user Caddy (guided mode): vauban never edits, restarts or recreates it. It is "ready" only when (a) a host dir is mounted at `/etc/caddy/sites`, (b) its Caddyfile contains `import /etc/caddy/sites/*.caddy`, (c) it is attached to network `vauban`. Otherwise apply stops before any server change and prints the guide.
- Caddy reload: `docker exec <caddy> caddy validate --config /etc/caddy/Caddyfile` then `docker exec <caddy> caddy reload --config /etc/caddy/Caddyfile`; on validate failure the site file is removed and nothing is reloaded.
- Install steps need passwordless sudo (`sudo -n`) and Debian/Ubuntu (`ID`/`ID_LIKE` contains `debian`); otherwise apply stops before any change with what to install by hand.
- GitHub secrets in this mode: `DEPLOY_HOST`, `DEPLOY_SSH_KEY`, `DEPLOY_DOMAIN`, `DEPLOY_KNOWN_HOSTS`, `DEPLOY_PORT`. Secret values only ever on stdin to `gh`; never printed.
- Generated deploy files carry a mode line: cloud files keep their current header; existing-mode files start with `# Generated by vauban (target: existing)`. vauban refuses to overwrite a deploy file generated for the other mode unless `--force`.
- `destroy` in this mode never removes Docker, Caddy, the network, the deploy user or other projects; keeps volumes unless `--purge`; only touches a project dir whose `.vauban-owner` equals this repo slug.
- No test touches a real server, cloud, GitHub or `$HOME` (set `HOME` to `t.TempDir()` where keys are involved). The sshd end-to-end test is opt-in (`VAUBAN_E2E=1`) and runs Docker detached with `--rm` and a timeout.
- Conventional Commits; commit trailer `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`.
- `go test -race ./...` and `golangci-lint run` green at every commit.

## Review Focus

- Changing `target` between `cloud` and `existing` while infra is applied (state has `infra_fingerprint`) must be refused like a cloud change, and never saved to vauban.yaml.
- An existing Caddy whose Caddyfile is baked into the image or on a named volume (no host bind for `/etc/caddy`): audit reports `user caddy: not editable`, apply stops with the guide, nothing written.
- Project name collision: `~deploy/apps/<project>` exists with another slug or no marker → apply and destroy both refuse, nothing changed.
- Host key changed after pinning (server reinstalled): SSH fails with a clear "host key changed for <host>; if expected, remove the line from .vauban/known_hosts" message, never silently re-trusts.
- SSH user without sudo on a server already fully set up (Docker, deploy user, Caddy ready): apply must succeed end to end without ever calling sudo.
